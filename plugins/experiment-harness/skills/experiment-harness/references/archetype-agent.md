# Archetype: Agent Competition

An engine or simulator, opponents, maps, and a ladder. Example: a Battlecode-style bot competition
where teams submit code that plays a turn-based strategy game under per-turn compute limits.

Differences from the prediction archetype: the "dataset" is self-generated by playing matches;
evaluation is relative to an opponent pool; the game may be unknown until launch and patched
mid-season; teams may include a strategist who writes hypotheses but not code.

---

## Directory Layout

```
CLAUDE.md
docs/
  task-spec.md               # = game spec: units, API, constants, win conditions, submission limits
  code-map.md                # repo anchor: runner, bot entry, snapshot/submit scripts
  arch-foundations.md        # language, engine version pin, allowed libraries
  eval-protocol.md           # opponent pool, map split, games per pairing, time-budget margin
  arch-strategy.md           # human/strategist's macro plan: opening, economy→military timing, win path
  arch-<domain>.md           # 3–5 game domains derived from the spec on launch day — never hardcoded
  meta-tracker.md            # dated observations of top ladder/sprint teams
  arch-harness.md
experiments/
bots/
  dev/                       # the only bot code Claude edits freely
  v001/ v002/ …              # frozen runnable snapshots (opponents); never edited
  params/                    # tunables per version, e.g. v012.json — logic ≠ parameters
eval/                        # match runner, stats, map lists — frozen
maps/{train,holdout}/
results/                     # gitignored raw match outputs
scripts/snapshot.sh  scripts/submit_gate.sh
.claude/rules/
```

Snapshots are folders (not only git tags) because several versions must run **simultaneously** as
opponents. Each snapshot is also tagged `vNNN`.

## Modes Specific to This Archetype

### Pre-launch (game not revealed)
Create only game-independent parts: eval runner with real working code against the current engine
(smoke-tested), experiment system, snapshot/eval/experiment rules, `eval-protocol.md`, CLAUDE.md with
Status and Deferred Components in `arch-harness.md`: `task-spec.md (game), arch-<domain>.md,
arch-strategy.md — create on launch day <date>` (no routing rows until they exist). Optional practice on the previous season's game lives in `practice/`, archived
on launch day; nothing from it is imported into `bots/`.

### Launch day
1. Fetch the official docs (use an `llms.txt` index if offered) → `task-spec.md`, stamped with engine
   version and date. Never carry mechanics over from a previous season.
2. Language decision (if several are allowed): record trade-offs in `task-spec.md` Constraints and
   the decision in `arch-foundations.md`. Default: the language the team can debug fastest, unless the
   spec makes compute clearly binding.
3. Derive 3–5 domains from the spec (e.g. pathing, economy, combat, communication); propose `paths`
   globs; human confirms.
4. Create domain docs, `arch-strategy.md` (starter baseline + first plan), domain rules.
5. Wire the runner to the new engine; EXP-000 = starter vs. starter on all maps.
6. Add routing rows for the new docs, clear their Deferred Components entries, update `code-map.md`.

### Engine patch
Spec Change procedure (`protocols.md`) + re-run the current best vs. pool to re-establish baselines.

## Eval Protocol Defaults to Propose

- **Opponent pool:** current best, last N adopted versions, starter bot, and style bots (rush /
  economy / turtle) once they exist. Never evaluate only against the previous version.
- **Map split:** train maps for experiments; holdout maps only for promotion. Recorded in
  `eval-protocol.md` (one home).
- **Games:** ≥ <N> per pairing per map side; Wilson 95% lower bound > 50% vs. current best on train
  maps AND not significantly worse on holdout → ADOPT. SPRT allowed for early stopping.
- **Time budget:** every candidate reports max and p99 turn time as % of the limit; above the
  margin (default 70%) → REJECT. Local timing ≠ ladder timing → run the engine's ladder-hardware
  test before submitting.
- **Ladder as out-of-sample:** log Elo 1–2 h after each submission. A local ADOPT that drops on the
  ladder signals pool bias → add the offending style to the pool.

## Strategist Workflow

- The strategist writes plain-language ideas in `experiments/INBOX.md` (tag `strategist`); no code
  reading needed.
- "process inbox" converts them into falsifiable hypotheses with prior-art checks, as usual.
- Replay observations: ladder opponents → `meta-tracker.md`; own losses → INBOX.
- Parameter tuning never edits logic files — only `bots/params/`.

## Extra Rule Files

```markdown
---
paths:
  - "bots/dev/**"
---
# Bot Code
- Obey submission constraints in `docs/task-spec.md` (imports, file I/O during turns, native
  extensions, size and file-count limits, allowed libraries).
- Per-turn compute: cache expensive searches; no full-map search every turn; measure turn time after
  structural edits.
- Tunables live in `bots/params/`, not as literals in logic.
Spec → `docs/task-spec.md`, plan → `docs/arch-strategy.md`
```

```markdown
---
paths:
  - "bots/v*/**"
---
# Snapshots
- Never edit a snapshot. To change behavior, edit `bots/dev/` and run `scripts/snapshot.sh` to
  create the next version.
```

## Status Block Additions

- Current best version + vs.-pool win rate (Wilson CI)
- Ladder Elo / rank, next sprint date
- Days until final submission; Mode normal | FREEZE (default freeze: 3 days before the deadline)

## Submission Gate (`scripts/submit_gate.sh`)

Snapshot exists and is tagged → package passes size/file/extension checks → ladder-hardware test
passes within the time margin → LOG.md row `submitted vNNN at <time>` → Elo recorded 1–2 h later.

## Postmortem Additions

Version lineage, local vs. ladder divergence per submission, which pool styles exposed weaknesses.
